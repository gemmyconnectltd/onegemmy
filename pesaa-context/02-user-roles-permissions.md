# 02 — User roles and permissions

## Kinds of users

| User | How identified (backend) | Scope | Notes |
|---|---|---|---|
| **Platform super-admin** | `users.is_superuser = true`, `tenant_id IS NULL`, `role = "superadmin"` | Whole platform (super-admin console, `/api/v1/admin/*`) | Guard `get_current_active_superuser` → `SuperUser` dependency (`backend/app/core/deps.py`). Extra fine-grained **platform permissions** for Data Management in `users.platform_permissions` (`data:view`, `data:preview`, `data:request`, `data:approve`, `data:execute`, `data:history`, `data:recovery` — `app/modules/admin/data_management/permissions.py`), granted with `scripts/grant_data_permissions.py`. |
| **Business owner** | `users.is_superuser = true` **with** a `tenant_id` (`role` usually `owner`) | Own business | Bypasses every role check in the backend (`require_permission`, `require_module_write`) and frontend (`hasPermission`). Sees the owner-only Dashboard and Business Reports. Only the owner may record a sale for another salesperson or change sale dates (`_require_owner`). |
| **Staff (employee)** | `is_superuser = false`, `tenant_id` set, `role_id` → a `roles` row | Own business, limited to their branches (`branch_id` / `branch_ids`) | Rights = role permissions + platform **baseline** (below) − modules switched off for that person (`users.disabled_modules`). `role` text (`admin`, `member`, `viewer`, …) is a legacy label also used in some checks. |

## Permission model

- **Permission = `resource:action`.** 58 resources × 5 actions (`create`, `read`, `update`, `delete`, `approve`) — `_PERMISSION_RESOURCES` / `_PERMISSION_ACTIONS` in `backend/app/modules/tenants/service/role.py`, stored in `permissions` and linked through `role_permissions`.
- Resources: `tenants, users, roles, permissions, departments, branches, billing, approvals, items, warehouses, stock, orders, pricing, returns, invoices, pos, chart_of_accounts, journal_entries, accounts_payable, accounts_receivable, banking, fixed_assets, budgeting, expenses, tax, employees, organization, recruitment, attendance, leave, payroll, performance, vendors, requisitions, rfq, purchase_orders, goods_receipt, contracts, leads, accounts, contacts, opportunities, activities, campaigns, tickets, bom, routing, mrp, work_orders, shop_floor, quality, costing, services, appointments, queue, service_commissions, discounts, credit`. Discounts also has extra actions in the UI (activate, apply, promotions, coupons, analytics, settings).
- **Modules → resources** (`MODULE_RESOURCES`, `backend/app/core/access.py`, mirrored in `frontend/src/lib/auth.tsx`): e.g. `sales` = orders, pos, invoices, returns, pricing, contacts, accounts, leads, opportunities, activities; `inventory` = items, warehouses, stock, pricing, returns; `pos` = pos; `discounts` = discounts.
- **Baseline for every active staff member** (`backend/app/core/permission_policy.py`): `read` + `update` on all 49 operational resources (`OPERATIONAL_VIEW_EDIT`), plus `CHECKOUT_CREATION` = `pos:create, orders:create, contacts:create, contacts:update, credit:create, discounts:apply, returns:create` (everyone who can use the till gets every selling feature). Consequence: **least privilege is only exact for create, approve and delete** — a role cannot take away read/update on operational data.
- **Delete** is reserved to owners/admins regardless of grants (`may_delete`, and the frontend `hasPermission` refuses `:delete` for other roles).
- **Per-user module switches:** `users.disabled_modules` (e.g. `["pos"]`) turns a module off for one person on top of their role; the owner is never affected.
- **Business features:** the plan/business module switches (`require_feature`, `GET /tenants/me/entitlements`) hide or block whole modules for the whole business (e.g. manufacturing, services, discounts).
- **Policies:** per-business approval rules in `tenants.approval_rules` (e.g. `own_sales_only`, `sale_approval`, `sale_no_self_approval`) change who sees/approves what.

## Built-in role templates

55 templates are seeded per business (`default_role_permissions` + `FOCUSED_ROLES` in `role.py`; doc `docs/ROLES.md`). Seeding adds missing roles only, never edits existing ones. Owners can create custom roles and per-user overrides (super-admin can give a user a dedicated role, `scope:"user"`).

## How permissions are enforced

### Backend (authoritative)

1. **Authentication:** `get_current_user` (`app/core/deps.py`) decodes the JWT (`type=access`), loads the user scoped to the token's `tenant_id`, rejects inactive users and suspended/pending businesses.
2. **Module gate on every tenant router** (`app/api_router.py`): `require_feature(module)` (business has the module) and `require_module_write(module)` (`app/core/access.py`):
   - user's `disabled_modules` contains the module → 403 "This feature has been switched off for your account".
   - `DELETE` → only owners/admins.
   - `GET` → needs any permission on a module resource (`decide_read`, with `READ_ALSO` exceptions so e.g. the till can read customers/VAT rates).
   - `POST/PUT/PATCH` → needs a matching action on a module resource (`decide`), with `EXACT` rules for sensitive paths (e.g. `POST /sales/orders` needs `orders:create` or `pos:create`; discount settings need `discounts:settings`; customer bulk import needs `contacts:create`) and `READ_ONLY_POSTS` (`/calculate/`, `/search`, `/preview`) treated as reads.
   - For POST, only **assigned** role grants count, except the explicit checkout list in `permissions_for_method` (`permission_policy.py`).
3. **Endpoint-level checks:** `dependencies=[Depends(require_permission("resource:action"))]` on sensitive routes (approvals, credit approval, discount rules, sales approve/void, salesperson change, etc.); owner-only helpers (`_require_owner`).
4. **Data scoping:** services always filter by `tenant_id`; branch scoping via `ActiveBranchId` (`X-Branch-Id` header validated against the user's branches); `own_sales_scope` limits non-approvers to their own sales when `own_sales_only` is on.
5. **Regression test:** `backend/tests/test_authz_sweep.py` calls every write endpoint as a user with no grants and fails if any succeeds or validates before authorizing.

### Frontend (presentation only)

- `useAuth()` (`frontend/src/lib/auth.tsx`): `hasPermission(p)`, `hasAnyPermission`, `hasModuleAccess(module)`, `isSuperAdmin()`, `isAdmin()`; `useCan()` (`lib/can.ts`).
- Menus filter items by feature, module access, permission and `ownerOnly` (`visiblePrimaryNavigation`, `visibleModuleLinks` in `lib/navigation.ts`); `ModuleAvailabilityGuard` redirects disabled URLs to the first allowed page.
- Buttons are hidden/disabled with `hasPermission(...)` (e.g. POS credit tab needs `credit:create`).

### Inconsistencies between frontend and backend

- `hasPermission` falls back to role **names**: `admin`/`owner` → everything; `viewer` → any `:read`; a user with an empty permission list → everything except a short blocklist. The backend has no such fallback, so the UI can show actions the server then refuses (403).
- `hasModuleAccess` returns true for `member` and `viewer` role names for every module, while the backend decides per resource.
- `isSuperAdmin()` in the ERP returns true for the **business owner** (`isSuperuser`) as well as the platform admin — the name is misleading.
- Frontend `MODULE_RESOURCES` is a manual copy of the backend map; drift is possible.
